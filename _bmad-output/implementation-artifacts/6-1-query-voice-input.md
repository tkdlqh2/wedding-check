# Story 6.1: 실행 중 질의 음성 입력 (FR-19)

Status: in-progress

## Story

As a 오퍼레이터,
I want 예식 진행 중 지금 상황을 타자 대신 말로 입력할 수 있기를,
so that 손이 자유롭지 않은 급박한 순간에도 질의를 포기하지 않는다.

## Acceptance Criteria

1. **Given** 실행 중 조회 화면의 질의창에서 **When** 음성 입력 버튼을 누르고 있는 동안 말한 뒤 손을 떼면 **Then** 인식된 문장이 질의 입력창에 채워지고, **자동으로 질의가 실행되지 않는다**(FR-19).
2. **Given** 음성 입력 버튼을 누르고 있는 동안 **When** 화면을 확인하면 **Then** 녹음 중임이 즉시(0ms) 드러나고 버튼은 ≥44px 탭 타깃이며, 손을 떼는 순간이 곧 녹음 종료다(UX-DR4, UX-DR19).
3. **Given** 마이크 권한이 거부되었거나 기기가 녹음을 지원하지 않을 때 **When** 음성 입력을 시도하면 **Then** 무엇이 막혔고 무엇을 하면 되는지가 즉시 드러나고, **타자 입력 경로는 그대로 살아 있다**(UX-DR14, AD-5).
4. **Given** 전사 요청이 실패하거나 인식 결과가 비어 있을 때 **When** 결과를 처리하면 **Then** 입력창의 기존 내용을 덮어쓰지 않고 명확한 오류가 표시된다.
5. **Given** 전사 요청이 진행 중일 때 **When** 음성 버튼이나 질의 버튼을 다시 누르면 **Then** 중복 요청이 발생하지 않는다(UX-DR13, UX-DR18).
6. **Given** 음성이 전사된 뒤 **When** 서버 저장 상태를 확인하면 **Then** 오디오도 전사 텍스트도 서버에 남지 않는다(NFR-5).
7. **Given** AD-1(벤더 중립)을 확인하면 **When** 구현을 보면 **Then** 전사 호출은 `lib/ai/ports.ts`의 포트를 거치고 `lib/services/*`는 벤더 엔드포인트를 알지 못한다(NFR-6).

## 이 스토리의 본질 — 입력 수단이 하나뿐인 화면

[query-panel.tsx](../../apps/web/app/operator/ceremonies/%5BhallId%5D/%5BceremonyId%5D/query-panel.tsx)의 질의 입력은 한 줄 `<input type="text">`가 전부다. 그런데 이 패널이 실제로 쓰이는 순간은 DESIGN.md §13이 기술한 그 순간이다 — 이서연(입사 2주 차)이 혼자 부스에 있고, 주례자가 방금 사전 협의 없이 순서를 바꿨고, 다음 큐가 몇 초 뒤다. **입력 수단이 타자 하나뿐이면 그 순간 이 기능은 없는 것과 같다.**

이 스토리는 새 AI 능력을 추가하지 않는다. 이미 있는 질의 파이프라인(3.3/3.4)의 **입력 경로를 하나 더 여는 것**이며, 검색·근거 제시·"관련 사례 없음" 안전장치는 전부 그대로다.

## 확정한 설계 결정

### D-1. 인식 엔진: 브라우저 내장이 아니라 OpenAI 전사 API

대표 결정(2026-08-03). 후보는 둘이었다.

| | Web Speech API (브라우저 내장) | OpenAI 전사 API |
|---|---|---|
| 비용/인프라 | 0 | 이미 있는 `OPENAI_API_KEY` 하나 |
| iPad Safari | **동작이 불안정하다고 알려져 있음 — 타깃 기기에서 무효가 될 위험** | `getUserMedia`+`MediaRecorder`는 iOS 14.3+ 표준 지원 |
| 실시간성 | 말하는 동안 즉시 | 손 뗀 뒤 1~3초 |
| 벤더 중립(NFR-6) | 브라우저에 종속 — 포트로 감쌀 수 없음 | AD-1 포트로 감쌈 |

**iPad가 타깃 기기(NFR-8)라는 사실이 결정적이다.** 이 제품의 실행 화면은 태블릿이 네이티브 존이고(DESIGN.md §8), 거기서 안 되는 인식 엔진은 나머지 장점이 무의미하다. 두 경로 병행(내장 우선 → 실패 시 API)도 검토했으나 **실패 계열이 두 배가 된다** — 이 코드베이스가 반복해서 배운 교훈(메모리 `fix-defect-class-not-instance`)의 반대 방향이라 택하지 않았다.

### D-2. Push-to-talk — 무음 자동 감지를 쓰지 않는다

예식장 부스는 음악·사회자 음성·하객 소음이 상시로 깔린 환경이다. "말이 끝났는지"를 무음으로 판정하는 방식은 이 환경에서 (a) 영원히 안 끝나거나 (b) 말 중간에 끊는다. **버튼에서 손을 떼는 순간이 곧 종료**라는 명시적 신호를 쓴다 — 오퍼레이터가 종료 시점을 100% 통제하고, 소음 수준과 무관하게 동작한다.

부수 효과로 UX-DR19("실행 화면에서 인지되는 지연은 곧 사용성 실패")도 만족한다 — 누르는 즉시 녹음이 시작되고, 떼는 즉시 멈춘다. 사이에 판정 로직이 없다.

### D-3. 인식 결과는 입력창에 채우고 **자동 제출하지 않는다**

대표 결정. 자동 제출이 손을 완전히 자유롭게 하는 건 맞지만:

- 오인식된 질의는 **무매칭으로 돌아온다.** "관련 사례 없음"은 이 시스템에서 정직함의 신호(DESIGN.md §2)인데, 오인식 때문에 그 카드가 뜨면 신입은 **실제로 사례가 없다고 믿는다.** 안전장치가 거짓 신호를 내는 것이며 §12-4("근거는 신성하다")를 정면으로 어긴다.
- 다시 말하는 비용 > 화면을 한 번 훑고 탭하는 비용. 급박한 순간일수록 후자가 싸다.

입력창에 채워지면 오퍼레이터는 **읽고 → 필요하면 고치고 → 질의하기**를 누른다. 탭 한 번이 추가되지만 그 탭이 오인식을 걸러낸다.

### D-4. `TranscriptionPort`를 AD-1 포트로 신설

`lib/ai/ports.ts`에 세 번째 포트를 추가한다. `lib/services/*`는 OpenAI의 `/v1/audio/transcriptions`도, 멀티파트 형식도 알지 못한다. `LLMPort`/`EmbeddingPort`가 확립한 구조 그대로이며, 어댑터는 기존 `lib/ai/adapters/openai.ts`에 함께 둔다(같은 벤더·같은 키·같은 fetch 관례).

### D-5. 오디오는 어디에도 저장하지 않는다 (NFR-5)

전사는 **요청 수명 안에서만** 존재한다 — Route Handler가 `FormData`로 받아 포트에 넘기고, 텍스트를 응답으로 돌려준 뒤 버린다. DB 테이블 없음, Blob 업로드 없음, 마이그레이션 없음. 로그에도 전사 텍스트를 남기지 않는다 — 질의 텍스트를 로그에서 제외한 3.4의 결정과 같은 이유이며, 실패 로그는 `toSafeErrorLabel()`을 거친다.

### D-6. 크기·길이 상한을 서버에서 강제한다

Vercel Functions의 요청 바디 상한(4.5MB)에 부딪히면 **원인이 불명확한 실패**가 된다. 클라이언트에서 녹음 시간을 상한(60초)으로 자동 종료하고, 서버에서도 바이트 상한을 독립적으로 검증한다 — 클라이언트 검증만 믿지 않는다(이 코드베이스의 기존 관례).

60초는 넉넉하다. 이 화면에서 말하는 문장은 "주례자가 순서를 갑자기 바꿨어요" 수준의 한 문장이다.

### 구현 중 확정한 것

**전사 모델은 `gpt-4o-mini-transcribe`.** 이 화면의 발화는 한 문장이라 최상위 모델이 필요하지 않고, 실행 화면에서는 지연이 곧 사용성이다(UX-DR19).

**확장자 매핑이 어댑터의 실질적 계약이다.** OpenAI 전사 API는 **파일명 확장자로 컨테이너를 판별한다** — MIME만 맞고 확장자가 없거나 틀리면 지원 형식인데도 400이 떨어진다. 그래서 `TRANSCRIBE_EXTENSIONS` 표가 있고, 테스트가 형식별 파일명을 고정한다.

**MIME 검증이 두 군데 있는 건 중복이 아니다.** 서비스는 "우리가 받기로 한 형식인가"(정책), 어댑터는 "벤더가 이 형식을 어떤 이름으로 아는가"(변환)다. 벤더가 바뀌면 어댑터 표만 바뀐다.

**`useSyncExternalStore`로 기능 탐지.** `useEffect` + `setState`는 eslint(`react-hooks/set-state-in-effect`)가 막고 cascading render를 만든다. 서버 스냅샷은 `true` — 하이드레이션 전에 비활성으로 그렸다가 활성으로 바뀌면 그 사이의 탭이 조용히 무시된다.

**`voiceBusy` 동안 질의 입력창도 잠근다.** 인식 결과가 입력창에 채워지는 사이 타자가 섞이면 무엇이 제출되는지 모호해진다 — 3.3이 in-flight 입력 잠금으로 해결한 것과 같은 계열이다.

**음성 실패 카드에는 액션 버튼을 두지 않는다.** 재시도 수단이 바로 위 마이크 버튼이고, "다시 시도"가 질의를 실행하면 무엇을 재시도하는지 어긋난다(3.4가 실패 종류별로 액션을 나눈 것과 같은 이유). 단, 세션 만료만은 로그인 링크로 분기한다.

### 검증

- **vitest 514건 통과**(458 → 514, **신규 56건**: 어댑터 14 / 서비스 21 / 컴포넌트 21). `tsc` / `lint` / `build` 클린, 라우트 `/api/query/transcribe`가 빌드 출력에 등록됨.
- **실서버 HTTP 종단**(프로덕션 빌드, 포트 3017, 실제 오퍼레이터 로그인):

| 시나리오 | 결과 |
|---|---|
| 미인증 | `401` |
| `audio` 파트 없음 | `400 invalid_input` |
| `audio/aac`(허용 목록 밖) | `400 지원하지 않는 오디오 형식입니다` |
| 64바이트 | `400 녹음이 너무 짧습니다` |
| 5MB | `413 녹음이 너무 깁니다` |
| 정상 형식 + 키 없음 | `502 transcribe_failed` |
| 실행 화면 SSR | 마이크 버튼·안내 문구·`aria-describedby` 렌더, **비활성 아님** |

- **NFR-5 확인**: 검증 실패 6종 중 로그가 남은 건 502 하나뿐이고 그 내용은 `{"event":"transcribe_failed","error":"Error"}` — 발화 내용도 벤더 응답 본문도 없다.

### 남은 공백 (명시)

- **실제 벤더 왕복은 로컬에서 검증하지 못했다** — 이 체크아웃의 `.env.local`에 `OPENAI_API_KEY`가 비어 있다. 어댑터의 요청 조립·응답 검증은 테스트가 고정하지만, **실제 한국어 인식 품질(예식장 소음 환경 포함)은 실키로 확인해야 한다.** Story 3.2/3.3이 남긴 것과 같은 성격의 공백이다.
- **iPad 실기기 검증 미완** — `MediaRecorder`가 iOS Safari에서 `audio/mp4`를 내는 경로는 코드·테스트로 다뤘지만, 실제 iPad에서 push-to-talk 제스처(포인터 캡처, 길게 누르기 콜아웃 차단)가 의도대로 동작하는지는 기기에서 봐야 한다. **파일럿 투입 전 필수 확인 항목.**
- **코덱스 리뷰 미실행** — 이 프로젝트의 스토리 파이프라인상 다음 단계.
