# PRD: 웨딩홀 스캔 오퍼레이터 인수인계 시스템
*Working title — confirm.*

## 0. 문서 목적

이 PRD는 웨딩홀 대표(의사결정자)와 이후 진행될 UX/아키텍처/에픽 단계 담당자를 대상으로 한다. 2026-07-23 현장 인터뷰 기록(비공개 — 저장소에 포함하지 않음)을 1차 입력으로 삼아 요구사항 수준으로 구체화했다. 이 문서는 그 내용을 중복 서술하지 않고 기능(FR)·성공지표(SM)로 번역한다. 용어는 §3 용어집에 고정하며, 본문 전체에서 동일 용어만 사용한다. 확정되지 않은 부분은 `[ASSUMPTION]`으로 표시하고 §12에 모아둔다.

## 1. Vision

웨딩홀 스캔(조명·음향·영상) 오퍼레이터의 인수인계는 현재 선임 동반 20~25회(약 1개월)가 걸린다. 인터뷰로 확인된 핵심은, 홀마다 고정된 "조작법"은 반복으로 금방 숙달되지만, 예식마다 달라지는 "변수 상황"(주례자 애드리브 등)에 대한 대응력은 20회를 반복해도 잘 줄지 않는다는 점이다. 즉 문제는 하나가 아니라 둘이며, 각각 다른 해법이 필요하다.

이 시스템은 두 문제를 분리해서 푼다. 정형 조작법은 홀별 체크리스트 템플릿과 선임의 시연 영상으로 표준화하고(순수 데이터 등록, AI 불필요), 변수 상황 대응은 선임의 암묵지를 예식 종료 후 자연어로 가볍게 기록하게 하고, 신입이 실제 예식 중 "지금 이런 상황인데 어떡해요?"라고 물으면 의미 기반으로 유사 과거 사례를 찾아 근거와 함께 제시한다. 선임 본인도 변수 상황을 정형화해서 기억하지 못한다는 사실이 인터뷰로 확인됐기 때문에, 자연어 입력이 이 시스템이 실제로 쓰이기 위한 전제조건이다.

## 2. Target User

### 2.1 Jobs To Be Done

- **오퍼레이터**로서, 예식 중 예상 밖 상황이 생겼을 때 동료에게 물어볼 수 없는 순간에도 근거 있는 대처법을 즉시 확인하고 싶다 (기능적).
- **오퍼레이터**로서, 실수로 예식을 망칠지 모른다는 불안 없이 현장에 단독 투입되고 싶다 (감정적).
- **오퍼레이터**로서, 매번 같은 설명을 말로 반복하지 않고, 겪은 변수 상황을 부담 없이 기록만 해두면 그게 동료에게 자동으로 전달되길 원한다 (사회적/기능적).
- **웨딩홀 대표**로서, 홀마다 다른 워크플로우를 일반화하기 어려웠던 문제를 이번엔 "우리 홀 전용"으로 풀고 싶고, 교육 기간 단축을 눈에 보이는 성과로 확인하고 싶다 (기능적/사업적).

### 2.2 Non-Users (v1)

- 다른 웨딩홀 사업체(타사)의 오퍼레이터 — v1은 단일 사업체 전용이다. 단, 사업체 내 여러 홀(예: 1층 홀, 2층 홀)은 지원한다 (§3 "홀" 참고).
- 고객(신랑·신부, 하객) — 이 시스템은 내부 교육 도구이며 고객 대면 기능이 없다.
- 스캔 외 직군(플래너, 헤어·메이크업 등) — 대상은 조명·음향·영상 오퍼레이터로 한정한다.

### 2.3 Key User Journeys

- **UJ-1. 오퍼레이터가 예식 중 낯선 상황에서 즉시 도움을 받는다.**
  - **Persona + context:** 입사 2주 차 오퍼레이터. 혼자 부스에 있고 동료는 다른 업무 중이다.
  - **Entry state:** 태블릿에 로그인된 상태, 오늘 예식의 체크리스트 인스턴스(UJ-3에서 생성됨)를 열람 중.
  - **Path:** 주례자가 사전 협의 없이 순서를 즉흥적으로 바꾼다 → 오퍼레이터가 조회 화면 하단 질의창에 "주례자가 순서를 갑자기 바꿨어요, 어떡하죠?"라고 입력 → 시스템이 과거 유사 변수 케이스(표현이 달라도 의미가 같은 것 포함)를 검색.
  - **Climax:** 화면에 "가장 유사한 과거 사례"와 그 사례의 사후 판단(어떻게 했어야 했는지 + 근거)이 함께 뜬다. 오퍼레이터는 그걸 보고 그 자리에서 대응한다.
  - **Resolution:** 예식은 큰 차질 없이 진행되고, 오퍼레이터는 이 상황을 나중에 피드백으로 남길 것이라는 걸 안다.
  - **Edge case:** 유사 사례가 없으면 "관련 사례 없음 — 선임에게 연락하세요"를 명확히 보여준다(억지로 엉뚱한 사례를 근거처럼 제시하지 않음). 이 문구는 시스템 권한과 무관하게, 현장에서 더 경험 많은 동료에게 연락하라는 실무 조언이다.

- **UJ-2. 오퍼레이터가 예식 직후 겪은 변수 상황을 말하듯 남긴다.**
  - **Persona + context:** 근속 1년 차 오퍼레이터. 방금 끝난 예식에서 실수 하나를 목격했다.
  - **Entry state:** 예식 종료 후 태블릿의 피드백 입력 화면.
  - **Path:** 자유 서술 텍스트 박스에 "축가 순서에서 반주가 늦게 나왔는데 오퍼레이터가 당황해서 음향을 늦게 올렸음. 미리 반주 큐를 30초 전에 걸어놨어야 함" 정도로, 정해진 폼을 채우지 않고 있었던 일을 그대로 입력.
  - **Climax:** 시스템이 이걸 단계/상황 설명/대처 결과/사후 판단/태그로 자동 구조화해서 보여주고, 오퍼레이터는 확인만 하고 저장한다.
  - **Resolution:** 이 사례는 즉시 UJ-1의 검색 대상에 포함된다.
  - **Edge case:** "지금 당장은 생각이 잘 안 난다"며 나중에 쓰겠다고 나가도, 임시 저장되어 나중에 이어 쓸 수 있다.

- **UJ-3. 대표가 홀 전용 체크리스트를 만들고 예식을 등록한다.**
  - **Persona + context:** 웨딩홀 대표. 이 시스템 도입 첫 주, 사업체 내 1층·2층 두 개 홀을 운영 중.
  - **Entry state:** 관리자 화면.
  - **Path:** 먼저 홀(1층 홀, 2층 홀)을 등록 → 홀을 선택한 뒤 그 홀 전용으로 단계별(사회자 멘트 → 신랑입장 → 주례 → 축가 → …) 항목을 등록하고 각 항목에 선임이 촬영한 시연 영상을 첨부(홀마다 장비·동선이 달라 항목 구성이 달라짐) → 예식 등록 화면에서 홀·날짜·계약 형태(주례 유무, 이벤트 추가 등)를 선택.
  - **Climax:** 선택한 홀·계약 형태에 맞는 항목만 조합된 "이번 예식 전용 체크리스트 인스턴스"가 자동 생성된다.
  - **Resolution:** 오퍼레이터는 이 인스턴스를 UJ-1에서 그대로 사용한다. 다른 홀의 템플릿 항목은 이 인스턴스에 섞이지 않는다.

- **UJ-4. 대표가 반복되는 문제 원인을 한눈에 확인한다.**
  - **Persona + context:** 웨딩홀 대표. 한 달간 운영 후.
  - **Entry state:** 관리자 인사이트 화면.
  - **Path:** 누적된 피드백(UJ-2)이 의미 기반으로 클러스터링되어 "이 원인이 N번째 반복되고 있다"는 목록으로 노출됨.
  - **Climax:** 표현이 서로 다른 피드백("주례자가 순서를 바꿈" / "목사님이 애드리브함")이 같은 항목으로 묶여 있는 걸 확인한다.
  - **Resolution:** v1에서는 읽기 전용 확인만 하고, 템플릿에 반영할지는 사람이 판단한다(자동 반영은 v2, §8.2 참고).

## 3. 용어집

- **홀** — 웨딩홀 사업체 내에서 예식이 진행되는 개별 공간 단위(예: 1층 홀, 2층 홀). 홀마다 장비·동선이 달라 체크리스트 템플릿이 별도로 관리된다. v1은 단일 사업체를 대상으로 하되 그 안의 다수 홀을 지원한다(§8.1 참고).
- **체크리스트 템플릿** — 홀 단위로 등록되는 재사용 가능한 단계별 항목 모음. 참고 영상·설명 텍스트를 포함. 오퍼레이터는 직접 편집하지 않는다(관리자 전용, §4.1 참고). 한 홀의 템플릿은 다른 홀의 템플릿과 독립적으로 관리된다.
- **체크리스트 인스턴스** — 특정 예식 1건에 대해 해당 예식이 속한 홀의 템플릿을 계약 형태에 맞게 조합해 생성된 실행용 사본. 예식마다 1개.
- **오퍼레이터** — 조명·음향·영상을 조작하는 현장 인력. 시스템 권한상 단일 역할이며, 신입·선임 구분 없이 실행 중 질의(FR-6/7)와 피드백 작성(FR-8/9)을 모두 수행한다(2026-07-24 결정 — 이전 신입/선임 구분은 폐기, §12 Assumptions Index 참고).
- **관리자** — 웨딩홀 대표. 홀·체크리스트 템플릿·예식 등록과 인사이트 조회 권한을 가지는 유일한 별도 역할.
- **변수 케이스** — 정형 체크리스트로 커버되지 않는 예식 중 돌발 상황과 그 대처에 대한 기록. 아래 피드백에서 생성된다.
- **피드백** — 예식 종료 후 오퍼레이터가 자연어로 남기는 변수 상황 기록. 시스템이 단계·상황 설명·대처 결과·사후 판단·태그로 자동 구조화한다.
- **실행 중 조회(질의)** — 오퍼레이터가 예식 진행 중 태블릿에서 자연어로 상황을 입력하고, 시스템이 의미상 유사한 변수 케이스를 근거와 함께 제시하는 기능.
- **인사이트** — 누적된 피드백을 의미 기반으로 클러스터링해 도출한 "반복되는 원인" 요약. v1에서는 읽기 전용이며 관리자만 본다.
- **계약 형태** — 예식 등록 시 선택하는 정형 필드(주례 유무, 이벤트 추가 등). 체크리스트 인스턴스 조합 규칙의 입력값.

## 4. Features

### 4.1 홀 관리 및 체크리스트 템플릿 관리

**Description:** 관리자(대표)가 사업체 내 홀(예식 공간)을 등록하고, 홀별로 체크리스트 템플릿을 등록·수정한다. 순수 CRUD와 파일(영상) 업로드로, AI가 관여하지 않는다. UJ-3의 앞부분을 실현한다. 한 사업체가 여러 홀(예: 1층 홀, 2층 홀)을 운영하는 경우, 각 홀의 템플릿은 서로 독립적으로 관리되며 섞이지 않는다(§3 "홀" 참고).

**Functional Requirements:**

#### FR-1: 홀 등록
관리자는 홀(예식 진행 공간)을 생성·수정·삭제할 수 있다.

**Consequences (testable):**
- 홀 저장 시 홀명은 필수다.
- 체크리스트 항목(FR-2)과 예식(FR-4)은 반드시 하나의 홀에 속하며, 홀을 지정하지 않고는 등록할 수 없다.
- 이미 템플릿 항목이나 예식이 연결된 홀은 삭제 시 처리 정책이 필요하다 `[ASSUMPTION: 연결된 데이터가 있는 홀은 삭제 대신 비활성화만 허용 — 대표 확인 필요]`.

#### FR-2: 체크리스트 항목 등록
관리자는 특정 홀에 속한 체크리스트 항목(단계명·설명·참고 영상)을 생성·수정·순서변경·삭제할 수 있다.

**Consequences (testable):**
- 항목 저장 시 소속 홀과 단계명은 필수, 참고 영상은 선택(영상 없이도 저장 가능).
- 항목은 등록된 홀에서만 조회·조합되며, 다른 홀의 인스턴스 생성에 영향을 주지 않는다.
- 항목 순서를 바꾸면 같은 홀에서 이후 생성되는 모든 신규 인스턴스에 반영된다(이미 생성된 인스턴스는 영향받지 않음).
- 검수용으로 심어둔 조작 시나리오 N개가 템플릿 항목으로 빠짐없이 커버된다(원문서 검수 기준과 동일).

#### FR-3: 시연 영상 업로드 및 연결
관리자는 항목별로 영상 파일을 업로드하고 재생 확인할 수 있다.

**Consequences (testable):**
- 업로드한 영상은 해당 항목 조회 시 바로 재생 가능하다.
- 지원 형식·용량 상한은 `[ASSUMPTION: 형식 mp4, 파일당 500MB 상한 — 실제 촬영본 확인 후 조정]`.
- 홀 간 영상 재사용(예: 두 홀의 카메라 조작법이 동일한 경우) 지원 여부는 `[ASSUMPTION: v1은 미지원, 홀마다 개별 업로드 — 실사용 빈도 확인 후 조정]`.

**Notes:** 계약 형태별로 어떤 항목이 포함/제외되는지 규칙(예: "주례 없음" 선택 시 주례 관련 항목 제외)을 관리자가 설정하는 화면이 필요 — `[NOTE FOR PM]` 이 규칙 설정 UX는 UX 단계에서 구체화 필요.

### 4.2 웨딩(예식) 등록 및 인스턴스 생성

**Description:** 관리자가 예식 1건을 등록하면, 선택한 홀·계약 형태에 맞춰 §4.1 템플릿에서 항목을 조합해 체크리스트 인스턴스를 자동 생성한다. 규칙 기반 조합으로 AI가 불필요하다. UJ-3을 실현한다.

**Functional Requirements:**

#### FR-4: 예식 등록
관리자는 홀·날짜·계약 형태(주례 유무, 이벤트 추가 등 정형 필드)를 입력해 예식을 등록할 수 있다.

**Consequences (testable):**
- 홀 선택은 필수이며, 저장 즉시 그 홀의 템플릿을 기반으로 체크리스트 인스턴스가 자동 생성되어 조회 가능하다.
- 동일 날짜에 여러 예식(같은 홀 내 복수 타임, 또는 서로 다른 홀)을 등록해도 각각 독립된 인스턴스를 가진다.

#### FR-5: 인스턴스 자동 조합
시스템은 예식이 속한 홀의 템플릿에서, 등록된 계약 형태에 맞는 항목만 골라 인스턴스를 구성한다.

**Consequences (testable):**
- "주례 없음"으로 등록하면 주례 관련 항목이 인스턴스에서 제외된다.
- 다른 홀의 템플릿 항목은 조합 대상에서 원천적으로 제외된다.
- 인스턴스 생성 후 수동으로 항목을 추가/제외하는 것도 가능하다(당일 변경 대응). 단, 수동 추가는 같은 홀의 템플릿 항목 범위 내로 제한된다 `[ASSUMPTION: 다른 홀 항목의 임시 차용은 v1 미지원]`.

### 4.3 실행 중 자연어 질의

**Description:** 오퍼레이터가 예식 진행 중 자연어로 상황을 물으면, 시스템이 §4.4에서 축적된 변수 케이스 중 의미상 유사한 것을 찾아 대처법과 근거를 제시한다. 키워드 일치가 아니라 의미 기반 매칭이어야 하는 이유는, 같은 상황도 사람마다 표현이 다르기 때문이다(§0 참고 원문서 근거). UJ-1을 실현한다. 이 PRD에서 AI가 실제 가치를 만드는 첫 지점이다.

**Functional Requirements:**

#### FR-6: 자연어 상황 질의
오퍼레이터는 실행 중인 체크리스트 인스턴스 화면에서 자유 텍스트로 현재 상황을 질의할 수 있다.

**Consequences (testable):**
- 질의 입력부터 응답 표시까지 `[ASSUMPTION: p95 5초 이내 — 실시간 예식 진행 중 사용이라는 성격상 지연이 치명적이므로 임의 상한을 둠, 대표 확인 필요]`.
- 표현이 다른 두 질의("주례자가 순서를 바꿈" vs "목사님이 애드리브함")가 같은 변수 케이스를 근거로 매칭되어야 한다.

#### FR-7: 근거 기반 응답
시스템은 매칭된 변수 케이스의 상황 설명·사후 판단(대처법+근거)을 함께 제시한다. 관련 사례가 없으면 "관련 사례 없음"을 명시하고 임의 사례를 근거처럼 제시하지 않는다.

**Consequences (testable):**
- 검수용으로 심어둔 변수 상황 질의 세트에 대해, 관련 없는 사례가 근거로 제시되는 경우가 0건이어야 한다(원문서 검수 기준과 동일).
- 유사 사례가 다건이면 유사도 상위 N건을 노출한다(N은 `[ASSUMPTION: 3건]`).
- 검색 범위는 `[ASSUMPTION: 예식이 속한 홀과 무관하게 사업체 전체 변수 케이스를 대상으로 검색하되, 결과에 발생 홀을 표시 — 변수 상황 대응은 장비보다 사람의 판단에 좌우된다는 가정, 대표 확인 필요(§11 참고)]`.

**Feature-specific NFRs:**
- 태블릿 환경, 예식장 내 네트워크가 불안정할 수 있다는 전제하에 오프라인/저속 회선에서의 동작은 §5 Cross-Cutting NFRs 참고.

### 4.4 예식 종료 후 피드백 등록

**Description:** 오퍼레이터가 예식 종료 후 자연어로 있었던 일을 그대로 말하듯 입력하면, 시스템이 단계/상황 설명/대처 결과/사후 판단/태그 스키마로 자동 구조화해 저장한다. 인터뷰에서 확인된 사실 — 작성자 본인도 변수 상황을 정형화해서 기억하지 못하므로 폼을 주면 안 쓴다 — 이 기능의 설계 전제다. UJ-2를 실현하며, §4.3의 데이터 원천이다.

**Functional Requirements:**

#### FR-8: 자연어 피드백 입력
오퍼레이터는 예식/단계를 선택한 뒤 자유 텍스트로 상황을 서술해 피드백을 남길 수 있다.

**Consequences (testable):**
- 정해진 폼 필드 채우기 없이, 자유 텍스트 하나만 입력해도 저장 가능하다.
- 입력을 완료하지 않고 나가도 임시 저장되어 이어 쓸 수 있다(원문서의 "지금 당장은 생각이 잘 안 난다" 케이스 대응).

#### FR-9: 자동 구조화
시스템은 입력된 자연어를 단계·상황 설명·대처 결과(잘 대처됨/잘못 대처됨)·사후 판단·태그로 자동 분해해 저장하고, 오퍼레이터에게 확인/수정 기회를 준다.

**Consequences (testable):**
- 검수용으로 심어둔 변수 상황 N건이 자연어 입력만으로 5개 필드 모두 정확히 채워져 저장된다(원문서 검수 기준과 동일).
- 오퍼레이터가 구조화 결과를 수정하면 수정된 값이 최종 저장된다(자동 구조화는 초안이지 확정이 아님).

**Feature-specific NFRs:**
- 피드백은 특정 오퍼레이터 개인을 지목하는 인사평가 기록이 아니라 "상황과 대처" 중심으로 저장된다 `[ASSUMPTION: 개인 실명 필드 없음 — §6 개인정보 참고, 대표 확인 필요]`.

### 4.5 빈도 기반 인사이트 (읽기 전용)

**Description:** 누적된 피드백을 의미 기반으로 클러스터링해 "이 원인이 N번째 반복되고 있다"는 주의사항 목록을 관리자(대표) 화면에 노출한다. v1은 읽기 전용이며, 이 결과로 §4.1 템플릿을 자동 변경하지 않는다(v2 범위, §8.2 참고). UJ-4를 실현한다.

**Functional Requirements:**

#### FR-10: 반복 패턴 클러스터링
시스템은 태그 완전 일치가 아니라 의미 기반으로 유사 피드백을 묶어 반복 횟수와 함께 노출한다.

**Consequences (testable):**
- 표현이 다른 반복 피드백(동의어·다른 서술)이 같은 인사이트 항목으로 묶여 노출된다(원문서 검수 기준과 동일).
- 각 인사이트 항목은 근거가 된 원본 피드백 목록을 펼쳐볼 수 있다(클러스터링 결과를 신뢰할 수 있도록).
- 클러스터링도 §4.3과 동일하게 사업체 전체 피드백을 대상으로 하되, 각 인사이트 항목에 발생 홀 분포를 함께 표시한다 `[ASSUMPTION, 대표 확인 필요(§11 참고)]`.

#### FR-11: 관리자 전용 노출
인사이트 화면은 관리자(대표) 권한에서만 접근 가능하며 오퍼레이터는 접근할 수 없다.

**Consequences (testable):**
- 오퍼레이터 계정으로 인사이트 화면에 접근 시도하면 차단된다.

## 5. Cross-Cutting NFRs

- **재현성**: 동일 질의(FR-6)·동일 피드백 입력(FR-8)은 재실행 시 동일한 결과를 반환한다(원문서 검수 기준과 동일).
- **성능**: FR-6의 응답 지연은 예식 진행을 막지 않는 수준이어야 한다 — §4.3 참고. 인사이트(FR-10) 클러스터링은 실시간일 필요 없음, 배치/주기 처리로 충분 `[ASSUMPTION: 일 1회 갱신]`.
- **가용성**: 예식은 취소·재시도가 불가능한 라이브 이벤트다. FR-6(실행 중 질의)가 응답하지 못하는 상황에서도 체크리스트 인스턴스 자체(정적 조회)는 계속 볼 수 있어야 한다 `[ASSUMPTION: 체크리스트 조회는 캐시/로컬 저장으로 네트워크 장애에도 동작, AI 질의만 영향받음 — 아키텍처 단계에서 구체화 필요]`.
- **검색 정확도**: FR-7(근거 기반 응답)과 FR-10(클러스터링) 모두 "의미 기반"이 요구사항이지 구현 방식(임베딩 등)은 아키텍처 단계에서 결정한다.

## 6. Constraints and Guardrails

**Privacy**
- 시연 영상(FR-3)은 오퍼레이터의 조작 시연이 목적이라 하객·신랑신부 얼굴이 노출될 가능성은 낮으나, 촬영 각도에 따라 포함될 수 있다 `[ASSUMPTION: 부스/장비 클로즈업 위주로 촬영, 인물 식별 최소화 — 실제 촬영 가이드는 v1 착수 시 확정]`.
- 피드백(FR-8~9)은 실제 발생한 실수를 기록하므로, 특정 개인을 징계 목적으로 지목하는 데 쓰이지 않도록 개인 실명이 아닌 "상황" 중심 스키마를 유지한다(§4.4 참고).

**Cost**
- FR-6(질의)는 예식당 호출 빈도가 낮아 비용 영향이 작다. FR-10(클러스터링)는 주기 배치 처리로 비용을 관리한다. 특정 LLM 벤더나 예산 상한은 확인된 바 없어 벤더 중립으로 둔다 `[ASSUMPTION]`.

**Safety**
- FR-7은 관련 사례가 없을 때 임의 사례를 근거처럼 제시하지 않는다 — 라이브 예식 중 잘못된 대처법이 확신을 가진 것처럼 제시되면 실제 사고로 이어질 수 있으므로, "모르면 모른다"고 답하는 것이 이 기능의 안전장치다.
- 이 안전장치가 "정보 제공"에 그치고 자동 개입까지 요구하지 않는 이유는 실패 비용이 이미 낮기 때문이다 — 원문서 진단상 고객 컴플레인은 현장에서 즉시 조치되고 환불·악성리뷰 사례가 없었다. 따라서 FR-7은 오퍼레이터의 판단을 돕는 수준이면 충분하고, 그 이상의 강한 가드레일(예: AI가 직접 조작을 대신하거나 승인 없이 경고를 발동하는 등)은 v1 스코프가 아니다.

## 7. Non-Goals (Explicit)

- 이직률 자체의 개선 — 인터뷰로 확인된 조기 이탈은 교육 강도와 무관한 사유이며 이 시스템의 스코프 밖이다.
- 네이티브 모바일 앱 — 태블릿/반응형 웹으로 충분하다(§2 폼팩터 결정 참고). v2에서도 다시 검토할 계획은 없다.
- 실시간 음성 인식/자동 대응 — 라이브 예식 현장의 소음·마이크 간섭을 감안해 질의는 텍스트 입력으로 고정한다.

## 8. MVP Scope

### 8.1 In Scope
- §4.1~4.5 전체 (홀 관리, 템플릿 관리, 예식 등록, 실행 중 질의, 피드백 등록, 인사이트)
- 단일 웨딩홀 사업체 기준 설계, 사업체 내 다수 홀(예식 공간) 지원 — 홀별 독립 체크리스트 템플릿(§4.1), 예식은 홀에 귀속(§4.2)
- 태블릿/반응형 웹

### 8.2 Out of Scope for MVP
- 다른 웨딩홀 사업체(타사)로의 확장 — 사업체 간 데이터 격리, 사업체별 관리자 계정·권한 분리 등 멀티테넌시는 v2 대상. 다만 §4.3·4.4의 변수 케이스 스키마·검색 로직은 재사용 가능하도록 설계(원문서 v2 참고).
- 인사이트 → 템플릿 자동 승격 및 승인 워크플로우 — v2 대상. `[NOTE FOR PM]` 원문서 저자가 명시적으로 다음 단계로 언급한 항목이라 우선순위 높음.

## 9. Rollout and Change Management

- 단일 사업체 파일럿으로 시작하며, 템플릿(§4.1) 초기 데이터는 홀별로 선임 인터뷰 기반으로 시딩해야 실사용이 가능하다 — 시스템 자체가 데이터를 만들어주지 않는다. 홀이 여러 개면 홀마다 이 시딩을 반복해야 한다.
- 도입 즉시 효과를 보려면 최소 1개 예식 주기(§4.2~4.4)를 실제로 돌려 변수 케이스가 어느 정도 쌓인 뒤에야 §4.3의 가치가 체감된다 `[NOTE FOR PM]` 초기 콜드스타트 기간의 기대치 관리가 필요.
- 대금·마일스톤 구조는 이 PRD 범위 밖이며, 별도 계약서에서 다룬다(원문서 §4 "다음 단계" 참고).

## 10. Success Metrics

**Primary**
- **SM-1**: 단독 투입까지 걸리는 예식 동반 횟수 — 현재 20~25회 → 목표 `[ASSUMPTION: 약 10회, 대표 확인 필요]`. Validates FR-6, FR-7.

**Secondary**
- **SM-2**: 실행 중 질의(FR-6~7)의 근거 매칭 정확도 — 검수용 변수 상황 세트에서 관련 없는 사례가 근거로 제시되는 비율 0%. Validates FR-7.
- **SM-3**: 피드백 자동 구조화 정확도(FR-9) — 검수용 세트에서 5개 필드 모두 정확히 채워지는 비율. Validates FR-8, FR-9.

**Counter-metrics (do not optimize)**
- **SM-C1**: 피드백 입력 소요 시간 — SM-3(구조화 정확도)을 올리려고 오퍼레이터에게 더 길고 자세한 서술을 요구하면 입력 자체를 안 하게 될 위험이 있다(원문서에서 확인된 "폼을 주면 안 쓴다"는 실패 패턴과 동일한 함정). 짧은 서술로도 구조화가 되는 방향을 유지해야 한다. Counterbalances SM-3.

## 11. Open Questions

1. SM-1의 목표 횟수(현재 10회로 가정)를 대표와 확정해야 한다.
2. 시연 영상·피드백 텍스트의 저장/보존 기간 정책이 없다 — 무기한 누적할지, 일정 기간 후 아카이브할지.
3. 예식 영상 촬영 시 하객/신랑신부 초상권 관련 사전 고지·동의 절차가 필요한지 홀 운영 정책 확인 필요.
4. 오퍼레이터가 퇴사할 경우 계정 회수 및 그 오퍼레이터가 남긴 데이터(질의 이력 등) 처리 정책.
5. 홀 내 네트워크 환경(와이파이 안정성)이 실제로 어느 정도인지 확인 필요 — §5 가용성 NFR의 전제.
6. 사업체 내 실제 홀 개수(현재 가정 2개, §2.3 UJ-3)를 대표와 확정해야 한다 — 홀 수는 §4.1 초기 시딩 규모에 직접 영향.
7. 변수 케이스 검색(§4.3)과 인사이트 클러스터링(§4.5)을 홀별로 분리할지, 사업체 전체로 통합할지 대표와 확정 필요 — 현재는 통합(홀 태그만 표시)으로 가정(§4.3 FR-7, §4.5 FR-10 참고). 홀마다 장비·동선이 크게 달라 변수 상황 대응법 자체도 다르다면 분리가 맞을 수 있음.
8. 홀 삭제 시 처리 정책(비활성화 vs 완전 삭제, §4.1 FR-1) 확정 필요.
9. 오퍼레이터 역할 통합(신입/선임 구분 폐기, §3 참고)이 실제 현장 인수인계 관행과 충돌하지 않는지 확인 필요 — 시스템 권한은 단일화하되, 신입이 실제로 선임의 실시간 감독 없이 피드백을 작성/수정하는 것이 현장에서 받아들여지는지 대표 확인 필요.
