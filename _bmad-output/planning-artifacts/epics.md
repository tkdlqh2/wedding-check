# 웨딩홀 스캔 오퍼레이터 인수인계 시스템 - Epic Breakdown

## Overview

이 문서는 PRD(`prd.md`), 아키텍처 스파인(`ARCHITECTURE-SPINE.md`), 디자인 시스템(`DESIGN.md`)의 요구사항을 구현 가능한 에픽·스토리로 분해한다.

## Requirements Inventory

### Functional Requirements

FR-1: 관리자는 홀(예식 진행 공간)을 생성·수정·삭제할 수 있다. — 홀명 필수, 체크리스트 항목/예식은 반드시 하나의 홀에 속함, 연결된 데이터가 있는 홀은 삭제 대신 비활성화만 허용.

FR-2: 관리자는 특정 홀에 속한 체크리스트 항목(단계명·설명·참고 영상)을 생성·수정·순서변경·삭제할 수 있다. — 소속 홀·단계명 필수, 영상은 선택, 항목은 등록된 홀에서만 조회/조합됨, 순서 변경은 이후 신규 인스턴스에만 반영.

FR-3: 관리자는 항목별로 영상 파일을 업로드하고 재생 확인할 수 있다. — 업로드 즉시 재생 가능, 형식 mp4/파일당 500MB 상한(가정), 홀 간 영상 재사용 v1 미지원.

FR-4: 관리자는 홀·날짜·계약 형태(주례 유무, 이벤트 추가 등)를 입력해 예식을 등록할 수 있다. — 홀 선택 필수, 저장 즉시 체크리스트 인스턴스 자동 생성, 동일 날짜 복수 예식도 각각 독립 인스턴스.

FR-5: 시스템은 예식이 속한 홀의 템플릿에서, 등록된 계약 형태에 맞는 항목만 골라 인스턴스를 구성한다. — "주례 없음" 시 관련 항목 제외, 다른 홀 템플릿 항목은 조합 대상에서 원천 제외, 생성 후 수동 추가/제외 가능(단 같은 홀 범위 내로 제한).

FR-6: 오퍼레이터는 실행 중인 체크리스트 인스턴스 화면에서 자유 텍스트로 현재 상황을 질의할 수 있다. — 응답 p95 5초 이내(가정), 표현이 다른 두 질의가 같은 변수 케이스로 매칭되어야 함(의미 기반).

FR-7: 시스템은 매칭된 변수 케이스의 상황 설명·사후 판단(대처법+근거)을 함께 제시한다. 관련 사례가 없으면 "관련 사례 없음"을 명시하고 임의 사례를 근거처럼 제시하지 않는다. — 관련 없는 사례가 근거로 제시되는 경우 0건, 유사도 상위 3건(가정) 노출, 검색 범위는 홀 무관 사업체 전체(가정, 발생 홀은 결과에 표시).

FR-8: 오퍼레이터는 예식/단계를 선택한 뒤 자유 텍스트로 상황을 서술해 피드백을 남길 수 있다. — 자유 텍스트 하나만으로 저장 가능(정해진 폼 필드 없음), 미완료 시 임시 저장되어 이어 쓸 수 있음.

FR-9: 시스템은 입력된 자연어를 단계·상황 설명·대처 결과(잘 대처됨/잘못 대처됨)·사후 판단·태그 5개 필드로 자동 분해해 저장하고, 오퍼레이터에게 확인/수정 기회를 준다. — 자동 구조화는 초안이며 오퍼레이터 확인/수정이 최종본; 확정(confirmed) 시점에만 변수 케이스가 생성됨(AD-8).

FR-10: 시스템은 태그 완전 일치가 아니라 의미 기반으로 유사 피드백을 묶어 반복 횟수와 함께 노출한다. — 표현이 다른 반복 피드백도 같은 인사이트 항목으로 묶임, 각 항목은 근거 원본 피드백 목록을 펼쳐볼 수 있음, 클러스터링도 사업체 전체 범위(가정, 발생 홀 분포 표시).

FR-11: 인사이트 화면은 관리자(대표) 권한에서만 접근 가능하며 오퍼레이터는 접근할 수 없다. — 오퍼레이터 계정으로 접근 시도 시 차단.

FR-12 (2026-07-27 추가, 어드민 프로토타입 리뷰 후속): 관리자는 예식 등록 시 신랑·신부 이름을 입력할 수 있다. — 예식을 홀·일시뿐 아니라 당사자 이름으로도 식별 가능해야 함.

FR-13 (2026-07-27 추가): 관리자는 예식 목록을 날짜별 캘린더로 필터링하고, 필터가 없을 때는 전체 예식을 페이지 단위로 조회할 수 있다. — 현재는 "오늘 예식"만 폼 바로 아래 flat list로 노출되어 과거/예정 예식을 찾을 방법이 없음.

FR-14 (2026-07-27 추가): 관리자는 오퍼레이터/관리자 계정을 조회하고 신규 오퍼레이터 계정을 생성·비활성화할 수 있다(회원 관리). — 현재 계정 발급은 개발자가 직접 실행하는 시드 스크립트가 유일한 경로.

### NonFunctional Requirements

NFR-1 (재현성): 동일 질의(FR-6)·동일 피드백 입력(FR-8)은 재실행 시 동일한 결과를 반환한다.

NFR-2 (성능): FR-6의 응답 지연은 예식 진행을 막지 않는 수준이어야 한다(p95 5초 이내, 가정). 인사이트(FR-10) 클러스터링은 실시간일 필요 없으며 배치/일 1회 갱신으로 충분하다.

NFR-3 (가용성): 예식은 취소·재시도가 불가능한 라이브 이벤트다. FR-6(실행 중 질의)가 응답하지 못하는 상황에서도 체크리스트 인스턴스 자체(정적 조회)는 계속 볼 수 있어야 한다(캐시/로컬 저장 기반, AI 질의만 네트워크 영향받음).

NFR-4 (검색 정확도): FR-7(근거 기반 응답)과 FR-10(클러스터링) 모두 의미 기반 매칭이 요구사항이다(구현 방식은 임베딩 기반으로 아키텍처 단계에서 확정됨).

NFR-5 (프라이버시): 피드백(FR-8~9)은 특정 개인을 징계 목적으로 지목하는 인사평가 기록이 아니라 "상황과 대처" 중심으로 저장되며, 개인 실명 필드를 두지 않는다.

NFR-6 (비용/벤더 중립): 특정 LLM 벤더에 종속되지 않고 교체 가능해야 한다(아키텍처 AD-1의 Ports-and-Adapters로 충족).

NFR-7 (안전성): FR-7은 관련 사례가 없을 때 임의 사례를 근거처럼 제시하지 않는다 — 라이브 예식 중 잘못된 대처법이 확신을 가진 것처럼 제시되는 것을 막는 핵심 안전장치(아키텍처 AD-8로 뒷받침).

NFR-8 (폼팩터): 태블릿(iPad) 최적화 반응형 웹. 네이티브 모바일 앱은 범위 밖.

### Additional Requirements

**스택/스캐폴딩 (Epic 1 Story 1에 영향)**
- Next.js 16.2.11+ (App Router, TypeScript), Vercel 배포 대상. 별도 CLI 스타터 템플릿은 지정되지 않음 — 표준 `create-next-app` 기반으로 스캐폴딩.
- Postgres + pgvector — Neon(Vercel Marketplace 경유), Preview/Production 브랜치 분리(AD-10).
- Drizzle ORM 0.31+ (`vector` 컬럼 + `cosineDistance` 지원 버전).
- better-auth — 세션 쿠키 기반 인증.
- @vercel/blob — 클라이언트 사이드 멀티파트 업로드(AD-4).
- @anthropic-ai/sdk — `claude-sonnet-5`(FR-6/7 실시간), `claude-haiku-4-5`(FR-9 배치, Message Batches API).
- Voyage AI `voyage-3.5` 임베딩, 1024차원 고정.

**아키텍처 구조 (전 스토리 공통 제약)**
- AD-1: 모든 LLM 생성·임베딩 호출은 `lib/ai/ports.ts`의 `LLMPort`/`EmbeddingPort`를 거친다. `lib/services/*`는 벤더 SDK를 직접 import할 수 없다(CI에서 import 경계 린트로 차단). 포트 시그니처: `LLMPort.generate()`, `LLMPort.generateStream()`, `EmbeddingPort.embed(texts: string[])`.
- AD-2: `lib/services/*`는 SQL/ORM을 직접 쓰지 않고 `lib/db/repositories/*`만 호출한다. 홀 종속 엔티티는 `hallId`를 필수 첫 인자로 받고 모든 쿼리에 `WHERE hall_id = $hallId`를 포함한다. `checklist_instances`는 `hall_id`를 자체 컬럼으로 저장(JOIN 대체 금지). `checklist_instance_items` 쓰기 경로는 `instance.hall_id = template_item.hall_id` 2-hop 재검증 필수.
- AD-3: 역할은 `operator`(질의+피드백+체크리스트 열람)와 `admin`(홀/템플릿/예식 CRUD+인사이트) 2종뿐. 세분화된 권한 티어 없음.
- AD-4: 영상 업로드는 `@vercel/blob/client` 클라이언트 사이드 업로드 사용, 서버는 바이트를 프록시하지 않음. `demo_videos` 행 쓰기는 반드시 `onUploadCompleted` 서버 콜백에서만.
- AD-5: 체크리스트 인스턴스는 최초 로드 성공 시 클라이언트 캐시(메모리/localStorage)에 저장, 오프라인/fetch 실패 시 캐시로 렌더링. 온라인 상태에서는 마운트 시 + 60초 간격 stale-while-revalidate. AI 질의/피드백 저장은 항상 온라인 필요, 실패 시 즉시 명시적 오류 노출(조용한 재시도 금지).
- AD-6: pgvector 유사도 검색·클러스터링은 홀 필터 없이 사업체 전체 대상, 결과에 `hall_id`를 표시용 태그로만 첨부.
- AD-7: `insight_clusters`는 오직 `lib/services/insight.ts::recomputeInsights()`만 쓸 수 있음. delete-then-reinsert 금지, upsert 방식, 동시 실행 방지 락 필요.
- AD-8 (안전 경계): `feedback` 테이블은 `status: draft | confirmed`를 가진다. `variable_case`는 오퍼레이터가 확정(`status='confirmed'`)한 시점에만 생성·임베딩되어 검색 인덱스에 들어간다. Draft는 절대 인덱스에 포함되지 않는다.
- AD-9: `checklist_template_items.applicable_contract_conditions JSONB` 컬럼으로 계약 형태 조건부 포함을 표현(부분집합 매칭). 정규화된 규칙 테이블은 채택하지 않음.
- AD-10 (배포/환경/배치): Neon 브랜치별 자동 분기(Preview/Production 격리), Drizzle 마이그레이션은 CI에서 배포 전 적용(실패 시 배포 차단), FR-10 배치는 Vercel Cron → `/api/cron/insight-recompute` Route Handler(공유 시크릿 헤더 보호, 장기 실행 워커 금지), AI 실패·저신뢰 응답은 구조화 JSON 로그, 시크릿은 환경별 분리 관리.

**데이터 모델 (Consistency Conventions)**
- 테이블: `halls`, `checklist_templates`, `checklist_template_items`, `demo_videos`, `ceremonies`, `checklist_instances`, `checklist_instance_items`, `feedback`, `variable_cases`, `insight_clusters` (영문 snake_case, `checklist_items` 같은 뭉뚱그린 이름 금지).
- PK는 UUID v4, 타임스탬프 ISO 8601 UTC, API 오류 응답은 `{ error: { code, message } }` 단일 봉투.
- 관리자 CRUD는 Server Actions, AI 질의/구조화는 Route Handler(스트리밍 가능). 인증은 better-auth 세션 쿠키 + 미들웨어 role 체크.

As a 관리자 또는 오퍼레이터,

**Then** 세션이 생성되고 역할(operator/admin)에 맞는 초기 화면으로 이동한다

**When** 관리자 전용 라우트에 접근하면
**Then** 접근이 차단된다(AD-3)

**Given** 프로젝트 스캐폴딩이 완료된 상태에서
**When** 화면을 렌더링하면

**When** 저장 버튼을 누르면

## Epic 2: 예식 등록 & 체크리스트 인스턴스 생성

관리자가 예식(홀·날짜·계약 형태)을 등록하면, 해당 홀 템플릿에서 계약 형태에 맞는 항목만 조합된 체크리스트 인스턴스가 자동 생성된다. 오퍼레이터는 태블릿에서 이 인스턴스를 열람할 수 있으며, 오프라인/네트워크 장애 시에도 캐시로 계속 조회 가능하다.

### Story 2.1: 예식 등록 (FR-4)

As a 관리자,
I want 홀·날짜·계약 형태를 입력해 예식을 등록할 수 있기를,
So that 그 예식에 맞는 체크리스트 인스턴스가 자동으로 준비된다.

**Acceptance Criteria:**

**Given** 홀이 최소 1개 등록되어 있을 때
**When** 홀·날짜·계약 형태(주례 유무 등)를 입력해 예식을 저장하면
**Then** 예식이 생성되고 즉시 체크리스트 인스턴스가 함께 생성된다

**Given** 홀을 선택하지 않고 저장을 시도하면
**When** 저장 버튼을 누르면
**Then** 저장이 거부된다

**Given** 같은 홀 또는 서로 다른 홀에 같은 날짜로 여러 예식을 등록하면
**When** 각각 저장하면
**Then** 서로 독립된 인스턴스를 가진다

**Given** 오늘 등록된 예식이 없을 때
**When** 예식 목록 화면을 열면

So that 불필요한 단계가 인스턴스에 섞이지 않는다.

**Acceptance Criteria:**

**When** 목록을 확인하면
**Then** 등록된 전체 예식이 예식 일시 역순으로 페이지네이션(또는 무한 스크롤, `[ASSUMPTION]` 태블릿/데스크톱 겸용이므로 페이지네이션 채택 — 무한 스크롤은 관리자 데스크톱 화면 관례에 안 맞음)되어 표시된다 — 등록 폼 바로 아래가 아니라 캘린더 아래로 위치 이동

**Given** 특정 날짜를 선택한 상태에서
**When** 선택을 해제(같은 날짜 재클릭 등)하면
**Then** 전체 목록 + 페이지네이션 상태로 돌아간다

### Story 5.3: 예식 등록 시 신랑·신부 이름 입력 (FR-12)

As a 관리자,
I want 예식 등록 폼에서 신랑·신부 이름을 입력할 수 있기를,
So that 예식을 홀·일시뿐 아니라 당사자 이름으로도 식별할 수 있다.

**배경:** `ceremonies` 테이블(`apps/web/lib/db/schema.ts`)과 등록 폼(`ceremony-form.tsx`) 어디에도 이름 필드가 없다. 마이그레이션 필요.

**Acceptance Criteria:**

**Given** 예식 등록 폼을 열면
**When** 필드를 확인하면
**Then** 신랑 이름, 신부 이름 입력란이 각각 있다

**Given** 신랑·신부 이름을 입력하고 저장하면
**When** 예식이 생성되면
**Then** 두 이름이 함께 저장된다(`[ASSUMPTION]` 폼에서는 필수 입력으로 처리 — 실제 예식은 항상 당사자가 있으므로; DB 컬럼 자체는 nullable로 두어 기존 예식 데이터와의 하위 호환을 보존)

**Given** 신랑 또는 신부 이름 중 하나를 비운 채 저장을 시도하면
**When** 저장 버튼을 누르면
**Then** 저장이 거부되고 필드 에러 스타일(1px solid #E0353B + 헬퍼 텍스트, UX-DR14)로 안내된다

**Given** 신랑·신부 이름이 저장된 예식이 있을 때
**When** 예식 목록(Story 5.2의 캘린더/페이지네이션 목록 포함)이나 예식 상세 화면에서 조회하면
**Then** 이름이 함께 표시된다

### Story 5.4: 회원(계정) 관리 (FR-14)

As a 관리자,
I want 오퍼레이터/관리자 계정을 화면에서 조회하고, 신규 오퍼레이터 계정을 생성·비활성화할 수 있기를,
So that 신입이 들어올 때마다 개발자에게 시드 스크립트 실행을 부탁하지 않고 직접 로그인 정보를 발급할 수 있다.

**배경:** 현재 계정 발급은 `apps/web/scripts/seed-accounts.ts`(개발자 전용 CLI)가 유일한 경로다. 로그인은 better-auth phone-number 방식(이메일 아님)이며 역할은 `operator`/`admin` 2종(AD-3). 내비게이션에 "회원" 항목 자체가 없다.

**Acceptance Criteria:**

**Given** 관리자로 로그인한 상태에서
**When** 상단 내비게이션의 "회원" 링크를 클릭하면
**Then** 회원 관리 화면으로 이동해 등록된 계정 목록(이름·전화번호·역할·활성 상태)을 볼 수 있다

**Given** 회원 관리 화면에서
**When** 이름·전화번호·초기 비밀번호를 입력해 신규 오퍼레이터 계정을 저장하면
**Then** 새 계정이 생성되고 목록에 나타나며, 그 전화번호+비밀번호로 실제 로그인이 가능하다

**Given** 이미 다른 계정이 쓰고 있는 전화번호로 신규 계정을 생성하려 하면
**When** 저장을 시도하면
**Then** 저장이 거부되고 "이미 등록된 전화번호입니다" 같은 구체적 오류가 표시된다

**Given** 계정을 비활성화하면(`[ASSUMPTION]` Story 1.2 홀 삭제 정책과 동일하게 완전 삭제 대신 비활성화)
**When** 그 계정으로 로그인을 시도하면
**Then** 로그인이 차단된다

**Given** 오퍼레이터 세션으로 회원 관리 화면 URL에 직접 접근을 시도하면
**When** 접근하면
**Then** 차단된다(AD-3)
